# E01 · Reading four RTX 4090 traces / 四组 GPU 空转实测

[Trace archive / 原始归档](e01-45288496471.zip) · [Owning run / 验收运行](https://github.com/jasonjiang8866/MLsysZero2Hero/actions/runs/45288496471) · [English exercise](../../lessons/e01/README.md) · [中文练习](../../lessons/e01/README.zh-CN.md)

On 24 November 2026 (Singapore), one RTX 4090 in EUR-IS-1 ran 16 steps × 262,144 FP32 values under PyTorch 2.9.0+cu128. Four unprofiled repetitions supply the timing medians. A separate profiler pass per case supplies kernel counts and gaps. / 计时来自每组四次无 profiler 重复的中位数。kernel 数和空隙取自另一次带 profiler 的运行。空隙为首末 kernel 之间没有 kernel 执行的累计时间。

| Case / 对照 | Kernels | Wall / 端到端 (ms) | Host thread CPU / 主机线程 (ms) | Gaps / 空隙 (ms) |
| --- | ---: | ---: | ---: | ---: |
| baseline | 16 | 0.185 | 0.181 | 0.597 |
| host_cpu | 16 | 48.256 | 48.254 | 45.674 |
| io_wait | 16 | 49.543 | 0.554 | 46.514 |
| small_launches | 512 | 3.353 | 3.350 | 3.282 |

**Host starvation.** In both producer cases, find the CPU annotation ending in `/producer` before the next launch. The device shows a similar gap in each. Thread CPU time distinguishes roughly 48 ms of busy work from a sleeping producer. The sleep models a blocked input reader. Diagnosing an actual storage problem would also require I/O evidence.

**主机供数。** 在两份 trace 的 CPU 轨道上找到以 `/producer` 结尾的区间，观察下一次 kernel 启动。两组 GPU 时间线都有约 3 ms 的间隔。线程 CPU 时间揭示了一组在忙算，另一组在睡眠。真实训练中要进一步归因于存储，还需采集 I/O 指标。

**Fragmented launches.** Compare the 16 `/step` ranges in baseline and small_launches. Splitting each addition into 32 pieces raises the kernel count from 16 to 512, with identical output. Wall time increases about 18× in this workload. Compare the unprofiled medians for that ratio. Profiling changes the schedule, especially for very short kernels.

**小算子启动。** 两组都是 16 步，每步切成 32 份后，kernel 从 16 增至 512，数值输出相同。这次工作负载的端到端耗时约为基线的 18 倍。这个倍数用无 profiler 的中位数计算，微秒级算子的时间线会受到采集本身影响。
